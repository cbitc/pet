# Issues —— issue 驱动的过程记录

> 本项目**先有 issue 文档，再动代码**：每一件值得记的变更都能在 `docs/issues/` 找到
> 「为什么做、做成什么样、怎么验证、当时怎么取舍」。全局规范见 [../conventions.md](../conventions.md)。

---

## 1. 工作流

```
提案 ──▶ 进行中 ──▶ 已关闭
  │         │            └─ 回写全局文档（domain / architecture / conventions）
  │         └─ 方案或验收变更写回本文档
  └─ 复制 TEMPLATE.md，编号，登记到下方索引
```

1. **开工前**：复制 [TEMPLATE.md](TEMPLATE.md) 为 `NNNN-slug.md`，写清背景、目标 / 非目标、
   验收标准，状态置 `提案`，并登记到本文索引。
2. **开工时**：状态改 `进行中`。
3. **实现中**：关键取舍写进「决策记录」；验收清单随进度勾选。
4. **完成时**：补齐「执行与结果」与「如何验证」，状态改 `已关闭`。
5. **回写全局**：行为、架构、规范发生变化时，同步更新 `../domain.md` / `../architecture.md` /
   `../conventions.md`；issue 文档只做过程与索引，**不复制**全局内容。

## 2. 命名、状态与元信息

| 项     | 约定                                                               |
| ------ | ------------------------------------------------------------------ |
| 文件名 | `NNNN-slug.md`：4 位序号 + 短横线 slug，如 `0003-idle-behavior.md` |
| 序号   | 本地顺序号，只增不减、永不复用；**不等待** GitHub Issue 先建       |
| 状态   | `提案` → `进行中` → `已关闭`；暂停用 `搁置`                        |
| 类型   | `特性` / `缺陷` / `重构` / `事故排查` / `调研` / `文档`            |
| 元信息 | 标题下一行固定写法：`> 状态：… · 类型：… · 日期：… · 关联：…`      |
| 关联   | 指向其他 issue 文档、GitHub Issue/PR、或 `文件:行号`               |

> 若工作对应 GitHub Issue：文档编号仍用本地序号，元信息里补 `GitHub #n` 链接即可——
> 文件名的职责是「在仓库里可寻址」，不承担外部跟踪器的编号。

## 3. 何时开 issue、何时不开

| 做                 | 例子                                                   |
| ------------------ | ------------------------------------------------------ |
| **开 issue 文档**  | 新功能、行为变更、重构、缺陷修复、事故复盘、跨模块调研 |
| **不开**（直接改） | 错别字、注释、单行格式修正；这类改动无需过程记录       |

事故排查（如 0001/0002）特别适合本格式：**症状 → 证据 → 根因 → 修复 → 回归点**，
目的是让后来者「改动前先读，不要回退」。
